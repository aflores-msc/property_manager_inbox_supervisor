Orchestrating a triage pipeline with LangGraph4j

A trace through java-app — Spring Boot 4, Spring AI 2, and LangGraph4j turning a Gmail inbox into a triaged, structured SQLite queue. The center of gravity is LangGraph4j: how a compiled graph actually executes a request, what its state model does and doesn't guarantee, and three real bugs that only surfaced once it ran against a live Gemini key and a real inbox.

Java 25 Spring Boot 4.1.1 Spring AI 2.0.1 LangGraph4j 1.8.27 JavaFX 25 + AtlantaFX sqlite-jdbc
Audience. Senior/staff engineers evaluating or building agentic systems on Spring Boot. This assumes you already know Spring's DI model, JavaFX's application lifecycle, and what a JSON schema is — it won't re-explain those. What it does explain in depth is the part most write-ups skip: how LangGraph4j's graph engine actually runs a request end to end, what it validates at compile time versus what it only discovers at runtime, and how that shows up as real bugs.

01

Architectural blueprint & domain flow

This is a Spring application context wearing a JavaFX window. That ordering matters: Spring's ApplicationContext is built first, inside the JavaFX launcher's own init() callback, and only once every bean — the Gmail client, the four LangGraph4j node classes, the JDBC repository, the compiled-on-demand graph factory — is fully wired does control pass to JavaFX's start(Stage) to actually draw a window. Dependency injection belongs to Spring end to end; JavaFX only ever owns the pixels.

The patterns holding it together

  • Router. ClassificationRouter is a pure function from state to a routing key — no side effects, trivially unit-testable in isolation from the graph that calls it.
  • Gateway. GmailEmailFetcher isolates every Google API type (GoogleAuthorizationCodeFlow, Gmail.Builder, MessagePart) behind one method returning a flat List<InboundEmail> — the seam where a different mail provider would slot in without touching the graph or the persistence layer.
  • Repository. TicketRepository opens a fresh JDBC connection per call rather than holding one open — not primarily for concurrency within this process (SQLite serializes writes at the file level regardless of how many local connections exist), but because property_manager.db is genuinely shared across processes with the separate Python app. Every connection sets a busy_timeout pragma, so a call that lands while the Python side briefly holds the file's write lock retries instead of failing outright with SQLITE_BUSY.
  • Command object via Task<T>. DashboardView runs the whole fetch-and-classify batch as one JavaFX Task on a single-threaded ExecutorService, using Task's built-in messageProperty()/progressProperty()/setOnSucceeded to get thread-safe UI updates without hand-rolling a signal mechanism.
02

LangGraph4j: the orchestration core

Everything upstream of the database funnels through one library. LangGraph4j is a Java-native graph engine purpose-built for exactly this shape of problem: a request that gets classified once, then handed to exactly one of several specialist handlers. This section is about the mechanics underneath EstateBeaconGraph.compile() — what actually happens when that method runs, and again when the resulting graph is invoked.

2.1 — LangGraph's vocabulary: graphs, state, nodes, edges, and loops

Before getting into how EstateBeaconGraph uses the library, it's worth naming the handful of concepts LangGraph (and its Java port, LangGraph4j) is actually built from — the same five ideas whether the graph is this app's one-shot classifier or a multi-turn, tool-calling agent.

  • State. One shared object — in practice a typed wrapper over a map — that every node reads from and writes to. It's the only thing that flows through the graph; nodes never call each other directly or pass their own return values around.
  • Node. A plain function: (state) → partial update. A node reads whatever keys it needs off the current state and returns the subset it wants changed. What a node actually does — call a model, hit an API, run a database query — is entirely up to the code inside it; LangGraph only cares about its signature.
  • Edge. A static wire from one node to the next: "after A finishes, always run B." A conditional edge is the dynamic version — a router function inspects the current state and returns the name of whichever node should run next, chosen from a fixed set of candidates (§2.4 below covers exactly how that name gets resolved).
  • Graph. The full collection of nodes and edges, built up declaratively (addNode, addEdge, addConditionalEdges) and then compiled once into something runnable. START and END are sentinel markers, not real nodes — every graph has exactly one entry edge from START, and execution stops the moment any path reaches END.
  • Loop. Nothing more than an edge that points back to a node already visited earlier in the same run. Nothing about a directed graph forbids revisiting a node — it's the mechanism LangGraph uses to express "keep going until some condition holds": an agent that calls a tool, reads the result, and decides whether to call another tool or answer, is a two-node loop between an agent node and a tool node, with a conditional edge doing the "call another tool, or stop" check on every pass.

Two things keep a loop from running forever. First, whatever the conditional edge's routing function reads has to actually change between passes — a tool's result gets written into state, a retry counter increments, something has to move for the "keep going" branch to eventually stop being chosen. Second, LangGraph4j (like LangGraph itself) enforces a maximum step count per invocation as a backstop, so a routing function with a genuine bug fails loudly with a recursion-limit error rather than hanging the process. Because state is just data flowing through ordinary function calls, the same object doubles as the unit of persistence: snapshot it after every node and a graph can be checkpointed, paused mid-loop, resumed later, or replayed from an earlier step — the machinery §2.7 below shows already running under this app, even though nothing here pauses or resumes today.

2.2 — State is a typed view over a map, not a class hierarchy

Every LangGraph4j graph carries a state type extending AgentState, which is fundamentally a wrapper around Map<String, Object>. PropertyManagementState adds nothing structural to that — no new fields, no schema annotations — only typed accessor methods built on AgentState's generic <T> Optional<T> value(String key):

excerpt from agent/PropertyManagementState.java 
public Optional<UniversalRoutingData> routingData() {
    return this.value(ROUTING_DATA);
}

public Optional<CityNoticeSchema> cityNotice() {
    return this.value(CITY_NOTICE);
}

Nothing enforces that ROUTING_DATA holds a UniversalRoutingData at the map level — the cast happens inside value()'s generic signature, at the call site. That's a real trade-off: the four constant strings (ROUTING_DATA, CITY_NOTICE, MAINTENANCE, DISPUTE) are the only thing keeping every node's writes and every accessor's reads pointed at the same keys, with no compiler check tying them together. What LangGraph4j buys in exchange is a state type that composes cleanly across an arbitrary graph shape: a node never needs to know the full state's type, only the handful of keys it reads and writes.

State merging between nodes defaults to simple overwrite unless a graph explicitly registers a Map<String, Channel<?>> schema — LangGraph4j's own examples use Channels.appender(ArrayList::new) to accumulate a running message list across nodes, the way a conversational agent would. EstateBeaconGraph never registers a channel schema at all, constructing its graph with a bare AgentStateFactory reference instead: every node here writes a distinct key exactly once, so there is nothing to accumulate and the default "last write wins" behavior is already correct.

2.3 — A node is a plain function; async wrapping is the graph engine's problem, not the node's

The contract a node implements is deliberately small:

org.bsc.langgraph4j.action.NodeAction 
public interface NodeAction <T extends AgentState> {
    Map<String, Object> apply(T state) throws Exception;
}

Every one of SupervisorNode, LegalAgentNode, MaintenanceAgentNode, and DisputeAgentNode implements exactly this — a synchronous method that reads whatever it needs off state and returns a partial update map. node_async(...), called once per node inside EstateBeaconGraph.compile(), adapts that into an AsyncNodeAction (a Function<S, CompletableFuture<Map<String,Object>>>) so the graph engine has one uniform async execution model regardless of whether a given node happens to block internally — which every node here does, on its own call to Spring AI's ChatClient. LangGraph4j has no awareness that Spring exists: it is handed a NodeAction instance at graph-build time and never inspects where that instance came from. Spring constructs each node class as an ordinary @Component, injecting a ChatClient into its constructor exactly like it would for any other bean; LangGraph4j just receives the finished object as a functional value.

2.4 — An edge decides the next node's name, as a string

Conditional routing is the same shape, one level up:

org.bsc.langgraph4j.action.EdgeAction 
public interface EdgeAction<S extends AgentState> {
    String apply(S state) throws Exception;
}

ClassificationRouter implements this directly — a pure function from state to a route key, with no CompletableFuture visible anywhere in its own code (deep-dive 4). edge_async(...) does the same adaptation node_async does for nodes. The part worth being precise about is what addConditionalEdges(sourceId, condition, mappings) actually does with the result: the string the condition returns is looked up as a key in the mappings map, and the corresponding value is the real target — either another registered node id, or the StateGraph.END sentinel. ClassificationRouter returns StateGraph.END directly for an IGNORED classification, so its own mapping entry is the identity pair END → END — not a redundant line, but the mapping correctly reflecting that the router's own return value already is the terminal sentinel, not an intermediate label that still needs translating.

2.5 — Compilation performs real structural validation

StateGraph.compile() is not a formality. addEdge and addConditionalEdges reject a source id equal to END immediately — a graph can never route away from the terminal state, only into it — and addConditionalEdges separately rejects an empty mappings map and a second conditional edge registered from a source that already has one. compile() then runs validateGraph(), which requires an edge from START to exist before it validates every other registered edge against the actual set of nodes added via addNode. The library's own test suite surfaces just how structural this gets — one assertion expects the exact message "parallel node doesn't support conditional branch, but on [A] a conditional branch on [A3] have been found!" when a graph tries to combine two shapes LangGraph4j considers incompatible.

The practical consequence for EstateBeaconGraph: if a fifth specialist were ever added to ClassificationRouter's enum and its routing map without a matching .addNode(...) call in compile(), the graph fails to compile with a GraphStateException naming the missing target — at graph-construction time, once, rather than as a routing failure discovered mid-request against a real email.

2.6 — Running the compiled graph: invoke() is the least of what CompiledGraph can do

CompiledGraph<State> exposes three execution modes: invoke(Map<String,Object>) — a single blocking call returning Optional<State>, used here — plus stream(...) and streamSnapshots(...), both returning an AsyncGenerator<NodeOutput<State>> that yields one item per node the graph actually visits. TicketProcessingService.process() only ever needs the final state for one email, with no UI requirement to show intermediate progress, so invoke() is the right call — but it means every intermediate NodeOutput LangGraph4j produces along the way (which node ran, what it changed) is computed and then discarded. stream() is the natural extension point if the dashboard ever wanted to show "classifying…" then "extracting maintenance details…" as an email works through the graph, since that data already exists inside the library — it simply isn't consumed today.

2.7 — The hidden cost of a compiled graph: state gets cloned between every step

LangGraph4j clones the current AgentState before applying every node's action, and again whenever it builds a NodeOutput or InterruptionMetadata — machinery inside CompiledGraph.AsyncNodeGenerator that runs on every step of every invocation, unconditionally. It is easy to assume this is part of the checkpointing/interruption/time-travel machinery and therefore gated behind configuring a BaseCheckpointSaver; it isn't. A checkpointer only gates one separate, additional call — addCheckpoint(), which persists a clone to the saver — so leaving it unconfigured (as this app originally did) removes that extra write, not the cloning itself. What actually controls the cloning is the graph's StateSerializer, chosen once at StateGraph construction time: the convenience constructor that takes just an AgentStateFactory — new StateGraph<>(PropertyManagementState::new), as this app originally did — implicitly picks ObjectStreamStateSerializer, which clones any value type it hasn't specifically registered by round-tripping it through ObjectOutput.writeObject(...), i.e. plain Java serialization. That makes Serializable a real, load-bearing requirement on every type that ever lands in state: not enforced by the compiler, and not visible until a graph actually executes with a non-serializable value sitting in it. This surfaced directly while building this app (§06) — a java.io.NotSerializableException thrown from deep inside AsyncNodeGenerator, for a reason nothing in LangGraph4j's public API signature warns about ahead of time. The graph now passes an explicit PropertyManagementStateSerializer — a small PlainTextStateSerializer that round-trips state through Jackson JSON — to the other StateGraph constructor, the one that takes a StateSerializer directly; a JSON round trip has no Serializable requirement, so none of the four schema records need to implement it any more.

2.8 — Why a graph engine, for one branch and no loops

With exactly one conditional fan-out and no cycles, this entire pipeline could be a switch statement inside a single service method — and for a codebase this size, that would compile and run identically. What a real graph engine buys instead: state and transitions become declared data (addNode, addEdge, addConditionalEdges calls LangGraph4j can introspect and diagram, rather than branches buried in imperative control flow) with genuine headroom already built in. LangGraph4j supports cycles, sub-graphs, checkpointed interruption, and human-in-the-loop pauses — none of which this pipeline uses, all of which are additional addNode/addEdge calls rather than a rewrite, the day a specialist needs to hand a case back to the supervisor for re-classification, or a city-notice response needs to pause for a human's sign-off before it's filed.

03

Spring AI: the model layer

LangGraph4j decides when a node runs; what each node does once it runs is entirely Spring AI's concern. Every one of the four nodes calls the same injected ChatClient the same way, differing only in the prompt text and the target record type.

3.1 — What useProviderStructuredOutput() actually opts into

Spring AI's default structured-output path is BeanOutputConverter: it generates a JSON schema from a target type using the victools generator, stuffs a textual description of that schema into the prompt, and forgivingly parses whatever text comes back — a necessary fallback for models with no native schema support. spec.useProviderStructuredOutput(), called in every node's .entity(...) invocation, opts out of that fallback: for a provider that supports it — Google GenAI, OpenAI, Anthropic, and Mistral, as of this Spring AI release — the schema is sent as an actual field on the API request, and the provider's own constrained decoder enforces it server-side rather than Spring AI parsing free text afterward. Confirmed live in this session, not just from documentation: a real Gemini key returned a correctly-typed UniversalRoutingData record on the first attempt, with the schema derived automatically from the record's own shape.

3.2 — Records supply both the wire schema and the prompt metadata

@JsonPropertyDescription on each record component isn't documentation — it's compiled directly into the JSON schema Spring AI hands the model, and the model conditions its extraction on that text the same way it would on an explicit few-shot instruction. One declaration on CityNoticeSchema.entityPhone — @JsonPropertyDescription("Contact phone number for the issuing authority") — does the job of both a Javadoc comment for a future maintainer and a targeted instruction for the model, at once.

3.3 — Prompt engineering: one flat text block, one real gap

Every node builds its prompt as a single Java text block passed to .user(prompt) — no SystemMessage/UserMessage split, no delimiter separating the classification instructions from the email body being classified. SupervisorNode (deep-dive 2) interpolates state.originalEmailText() — the full, untrusted body of an externally-received email — directly into the same string as the instructions telling the model how to behave. That is a concrete prompt-injection surface: nothing structurally stops an email's own body from containing text a model could read as an instruction rather than content to classify, and there is no role-based signal in the request separating the two. Fixing it would mean moving the instructions into an actual SystemMessage and the email content into a separate UserMessage, which Spring AI's ChatClient supports directly but none of the four nodes currently use.

04

Java 25 & Spring Boot 4 runtime

4.1 — Pattern matching makes the routing table's completeness a compiler fact

ClassificationRouter resolves a classification with an exhaustive switch expression over the Classification enum:

excerpt from agent/ClassificationRouter.apply 
.map(routing -> switch (routing.classification()) {
    case CITY_NOTICE -> LEGAL_AGENT;
    case MAINTENANCE -> MAINTENANCE_AGENT;
    case TENANT_DISPUTE -> DISPUTE_AGENT;
    case IGNORED -> StateGraph.END;
})

Because classification() returns the enum type rather than a raw string, the compiler requires every constant to have a matching case — there is no default branch, and none is needed. Add a fifth value to Classification without touching this file and the build fails here specifically, at the one place a human needs to decide where the new category routes. That's a mechanical correctness property, not a style preference: an unhandled case is a compile-time error, not a value silently falling through to a default at runtime.

4.2 — Records as both the schema and the serialization contract

UniversalRoutingData, CityNoticeSchema, MaintenanceSchema, and DisputeSchema are records — immutable and structurally transparent. They started out each declaring implements Serializable (§2.7's first finding): the graph's default StateSerializer clones every state value with plain Java serialization, and a record gets no special exemption from that requirement just for being a record — the interface has to be declared explicitly, the same as on any other class. That requirement went away once the graph switched to a JSON-based StateSerializer (§2.7): none of the four records implement Serializable today, since a JSON round trip only needs Jackson to see their fields, not the JDK's serialization mechanism.

4.3 — Spring Boot 4's baseline, mostly invisible here

Spring Boot 4.1.1 sits on Spring Framework 7 and a Jakarta EE 11 baseline, but that shift is invisible to an app with no servlets and no JPA. The one place it was directly felt: Jackson now ships as two coexisting major versions on the classpath — com.fasterxml.jackson.core:jackson-databind:2.21.5 for Spring's own JSON handling, and the renamed-groupId tools.jackson.core:jackson-databind:3.1.5 for Spring AI's schema tooling. jackson-annotations, notably, kept its original com.fasterxml.jackson.annotation package through that split — the only reason @JsonPropertyDescription imports the way it always has, unaffected by which Jackson major version processes it downstream.

4.4 — The one coupling this integration creates: whose thread is this?

Spring constructs singleton beans during context refresh — which, in this app, happens inside EstateBeaconApp.init(), called by the JavaFX launcher before the JavaFX Application Thread is guaranteed ready for Node construction. A @Component that builds real TableView/Button instances as field initializers is completely idiomatic Spring and wrong for JavaFX at the same time — the two frameworks' threading assumptions simply don't line up by default. This is exactly the failure mode covered as a critical, found-and-fixed bug in §06.

Two lifecycles, stitched into one entry point

EstateBeaconApp.java whole file 
@SpringBootApplication
@ConfigurationPropertiesScan
public class EstateBeaconApp extends Application {

    private ConfigurableApplicationContext springContext;

    public static void main(String[] args) {
        launch(args);
    }

    @Override
    public void init() {
        springContext = new SpringApplicationBuilder(EstateBeaconApp.class)
                .headless(false)
                .run(getParameters().getRaw().toArray(new String[0]));
    }

    @Override
    public void start(Stage stage) {
        Application.setUserAgentStylesheet(new PrimerDark().getUserAgentStylesheet());
        springContext.getBean(DashboardView.class).show(stage);
    }

    @Override
    public void stop() {
        springContext.close();
        Platform.exit();
    }
}
Pattern
One class answers to two frameworks: @SpringBootApplication makes it a valid component-scan root, while extends Application makes it a valid JavaFX launch target. launch(args) is JavaFX's own static bootstrap — it is what invokes init() and then start(Stage) on the correct threads, not Spring.
How the abstractions drive behavior
headless(false) stops Spring Boot from assuming a server environment and disabling UI-related autoconfiguration it would otherwise switch off by default. springContext.getBean(DashboardView.class) is the one moment the two frameworks actually hand off to each other — a fully-constructed, dependency-injected view object crossing from Spring's world into JavaFX's.
Edge case
Nothing catches a construction failure here. If SpringApplicationBuilder(...).run(...) throws — as it did, repeatedly, while diagnosing the bugs in §06 — the exception propagates out of init() as an unhandled JavaFX launch failure with a Spring stack trace underneath it, a jarring mix of two frameworks' error-reporting conventions for an end user to ever see.

Structured extraction via ChatClient

agent/AbstractLlmExtractionNode.java apply() 
@Override
public final Map<String, Object> apply(PropertyManagementState state) {
    try {
        T result = chatClient.prompt()
                .user(buildPrompt(state))
                .call()
                .entity(resultType, spec -> spec.useProviderStructuredOutput());
        return Map.of(resultKey, result);
    } catch (Exception e) {
        log.error("{} failed", name, e);
        return Map.of(PropertyManagementState.ERROR, name + " extraction failed: " + e.getMessage());
    }

Pattern
This is now the only place .entity(...) is called anywhere in the app. SupervisorNode, LegalAgentNode, MaintenanceAgentNode, and DisputeAgentNode all extend this class; each supplies just a prompt (via the abstract buildPrompt(state)), a target record type, a state key, and a name through the constructor — SupervisorNode's entire body is now a constructor call, super(chatClient, UniversalRoutingData.class, PropertyManagementState.ROUTING_DATA, "Supervisor node"), plus a buildPrompt() override holding the same prompt text this deep-dive originally quoted inline. .entity(resultType, ...) still does the same double duty described in §3.1: generating the schema Gemini decodes against, and deserializing the response into the same type — resultType is just a Class<T> parameter now instead of a type baked into four separate call sites.
How Spring AI is driving it
chatClient is still injected, not constructed here — each concrete subclass takes it as a constructor parameter and forwards it via super(...). The autoconfiguration story is unchanged: a one-method @Configuration class calls ChatClient.Builder.build(), with the builder itself wired by spring-ai-starter-model-google-genai from whatever spring.ai.google.genai.* properties are active. Nothing in this class hard-codes that the model is Gemini.
Edge case
The catch (Exception e) is still deliberately broad, for the same reason as before: it converts a schema violation, a network failure, and a quota error into one identically-shaped error entry in the returned state map, trading diagnostic precision for a graph that never crashes on one bad email. What changed is where that trade-off lives: this method used to be copy-pasted four times — once per node, each with its own prompt text interleaved into the same try/catch/log/return shape — a duplication a later review pass flagged directly (not a runtime bug, so it isn't in §06's list; a reuse finding instead). Collapsing it here means the next change to that error-handling contract, like adding a retry, is now a one-place edit instead of a four-place one.

Compiling the graph — once

agent/EstateBeaconGraph.java constructor 
public EstateBeaconGraph(
        SupervisorNode supervisorNode,
        LegalAgentNode legalAgentNode,
        MaintenanceAgentNode maintenanceAgentNode,
        DisputeAgentNode disputeAgentNode
) throws GraphStateException {
    StateGraph<PropertyManagementState> graph = new StateGraph<>(new PropertyManagementStateSerializer())
            .addNode("supervisor", node_async(supervisorNode))
            .addNode(ClassificationRouter.LEGAL_AGENT, node_async(legalAgentNode))
            .addNode(ClassificationRouter.MAINTENANCE_AGENT, node_async(maintenanceAgentNode))
            .addNode(ClassificationRouter.DISPUTE_AGENT, node_async(disputeAgentNode))
            .addEdge(START, "supervisor")
            .addConditionalEdges(
                    "supervisor",
                    edge_async(new ClassificationRouter()),
                    java.util.Map.of(
                            ClassificationRouter.LEGAL_AGENT, ClassificationRouter.LEGAL_AGENT,
                            ClassificationRouter.MAINTENANCE_AGENT, ClassificationRouter.MAINTENANCE_AGENT,
                            ClassificationRouter.DISPUTE_AGENT, ClassificationRouter.DISPUTE_AGENT,
                            END, END
                    )
            )
            .addEdge(ClassificationRouter.LEGAL_AGENT, END)
            .addEdge(ClassificationRouter.MAINTENANCE_AGENT, END)
            .addEdge(ClassificationRouter.DISPUTE_AGENT, END);

    this.compiledGraph = graph.compile();
}
Pattern
new StateGraph<>(new PropertyManagementStateSerializer()) — the graph's structure never changes at runtime, so building and compiling it belongs at bean-construction time, not per request. EstateBeaconGraph now holds the resulting CompiledGraph<PropertyManagementState> in a field and returns the same instance from every call to its compiledGraph() accessor, which TicketProcessingService.process() calls once per email and hands straight to invoke(...). See §2.2 for why no explicit channel schema is registered here, and §2.7 for why the serializer is passed explicitly rather than via the AgentStateFactory-only constructor.
How the abstractions drive behavior
Four addNode calls register every node the graph can ever visit; compile() (§2.5) checks the conditional-edge mapping's three specialist targets and its END entry against exactly that set. Get the string constants in ClassificationRouter and this map out of sync, and the mismatch is caught here, not mid-request — and because this now runs once, at Spring context startup, a malformed graph fails the application before a window ever opens rather than on whatever email happens to be first through the pipeline.
Edge case
This constructor throwing GraphStateException is a real behavior change from a plain no-arg constructor: Spring's bean creation fails, and the whole application fails to start, on a malformed graph. That's the intended trade — the previous shape (a compile() method called fresh on every single email, discovered during a later review pass rather than by a crash, since compilation itself is cheap structural validation with no network I/O) delayed that exact same failure to the first email routed through it instead of catching it at startup, and paid a redundant graph-construction cost on every invocation for no benefit, since nothing about the graph's shape depends on which email is being processed.

The routing decision, as an exhaustive switch

agent/ClassificationRouter.java class body 
public class ClassificationRouter implements EdgeAction<PropertyManagementState> {

    public static final String LEGAL_AGENT = "legal_agent";
    public static final String MAINTENANCE_AGENT = "maintenance_agent";
    public static final String DISPUTE_AGENT = "dispute_agent";

    @Override
    public String apply(PropertyManagementState state) {
        return state.routingData()
                .map(routing -> switch (routing.classification()) {
                    case CITY_NOTICE -> LEGAL_AGENT;
                    case MAINTENANCE -> MAINTENANCE_AGENT;
                    case TENANT_DISPUTE -> DISPUTE_AGENT;
                    case IGNORED -> StateGraph.END;
                })
                .orElse(StateGraph.END);
    }
}
Pattern
See §4.1 for the exhaustiveness guarantee this switch gets from routing on the Classification enum rather than a raw string. The Optional::map chain handles "the supervisor node failed, so there's no routing data at all" the same way the terminal case inside the switch handles a successful IGNORED classification — both fold to StateGraph.END, for different reasons.
How LangGraph4j is driving it
This class implements the synchronous EdgeAction<S> interface directly (§2.4); EstateBeaconGraph wraps an instance of it with edge_async(...) before handing it to addConditionalEdges. The router itself never touches a CompletableFuture — that's entirely the wrapper's concern, which is exactly what makes this class trivial to unit-test by constructing a PropertyManagementState directly and calling apply() on it.
Edge case
Add a fifth Classification constant without adding a case here, and the build fails at this switch specifically — not at a routing-map mismatch discovered by compile() elsewhere, but at the compiler, before either type is even a runtime concern.

OAuth2 desktop flow

email/GmailEmailFetcher.java connect() 
public void connect() throws IOException, GeneralSecurityException {
    var httpTransport = GoogleNetHttpTransport.newTrustedTransport();
    var jsonFactory = GsonFactory.getDefaultInstance();

    var credentialsFile = AppPaths.appFile("credentials.json").toFile();
    if (!credentialsFile.isFile()) {
        throw new FileNotFoundException(
                "OAuth credentials file not found at '" + credentialsFile
                        + "'. Download it from the Google Cloud Console and place it there.");
    }

    GoogleClientSecrets clientSecrets;
    try (var reader = new FileReader(credentialsFile)) {
        clientSecrets = GoogleClientSecrets.load(jsonFactory, reader);
    }

    var tokenStore = new FileDataStoreFactory(AppPaths.appFile("tokens").toFile());
    var flow = new GoogleAuthorizationCodeFlow.Builder(httpTransport, jsonFactory, clientSecrets, SCOPES)
            .setDataStoreFactory(tokenStore)
            .setAccessType("offline")
            .build();
    var receiver = new LocalServerReceiver.Builder().setPort(8888).build();
    Credential credential = new AuthorizationCodeInstalledApp(flow, receiver).authorize("user");

    this.service = new Gmail.Builder(httpTransport, jsonFactory, credential)
            .setApplicationName(APPLICATION_NAME)
            .build();
}
Pattern
Gateway construction, isolated to exactly one method — everything above the final Gmail.Builder call exists only to produce one authenticated Credential. This is the only place in the codebase that knows Gmail's OAuth client library exists at all.
How the Google client library is driving it
FileDataStoreFactory manages its own on-disk token cache under ~/.property_manager_ai/tokens/, in its own serialization format, refreshing a stored token automatically once setAccessType("offline") has secured a refresh token on first authorization — the reason a user only has to click through the OAuth consent screen once.
Edge case
LocalServerReceiver.Builder().setPort(8888) hard-codes the OAuth redirect port with no fallback. If anything else on the machine is already bound to 8888 when a fresh (non-cached) authorization is actually needed, this throws a bind exception with no message connecting it back to "something else is using 8888" — a rough edge for a desktop tool that otherwise fails with an actionable message, as the missing-credentials.json branch two lines above it does.

Bugs found running it live

Every finding below happened in this session, against a real Gemini key and a real Gmail inbox, and was fixed and re-verified before being written down here — not a code-review guess.

Critical — found & fixed LangGraph4j snapshots state with Java serialization; the schema records weren't Serializable

First real run threw java.io.NotSerializableException: com.estatebeacon.model.UniversalRoutingData from inside CompiledGraph$AsyncNodeGenerator. Reading the library's own internals confirmed why (§2.7): the graph's default StateSerializer clones AgentState values between every step using ObjectOutputStream-based serialization — unconditionally, regardless of whether a checkpointer is configured — and a Java record gets no free pass on Serializable just for being a record. The first fix, declaring implements Serializable on all four schema records, worked but only patched the symptom. The real fix, applied afterward: swap in PropertyManagementStateSerializer, a JSON-based StateSerializer built on Jackson, so state cloning never needs Serializable in the first place. A full graph invocation was re-run afterward and returned correct UniversalRoutingData and MaintenanceSchema values with no error, and the four schema records no longer implement Serializable.

Critical — found & fixed JavaFX controls were constructed off the FX Application Thread

DashboardView's TableView, Button, and other controls were originally instance-field initializers — idiomatic for a Spring @Component, and wrong for JavaFX, since Spring constructs singleton beans during context refresh inside EstateBeaconApp.init(), before the FX Application Thread is guaranteed ready for Node construction. Fixed by deferring every JavaFX object's construction into buildRoot(), which only ever executes from show(Stage), itself only ever called from Application.start() on the correct thread — the seam described in §4.4.

Critical — found & fixed Gmail batching assumed no inbox would exceed 100 unread messages

A later pass rewrote fetchUnreadEmails() to page through every unread message and fetch bodies via a single BatchRequest instead of one blocking call per message. First real run against a 228-message unread inbox threw 400 Bad Request straight from Gmail: "Inner request count exceeds the limit. Received: 228, Limit: 100" — Gmail caps a batch at 100 inner requests, undocumented anywhere in the client library's own types. Fixed by chunking the message-id list into MAX_BATCH_SIZE-sized groups, one BatchRequest per chunk.

Moderate — found & fixed EnvironmentPostProcessor registration used the wrong Spring Boot 4 mechanism

Spring Boot 4 moved EnvironmentPostProcessor to a new package (org.springframework.boot.EnvironmentPostProcessor), which reads as a signal to register it via the newer META-INF/spring/<interface>.imports convention other autoconfiguration classes use. That's wrong for this specific interface: decompiling spring-boot-4.1.1.jar showed SpringFactoriesEnvironmentPostProcessorsFactory still looks the class up under the classic META-INF/spring.factories key. The dotenv bridge silently never ran until this was corrected — the Spring context started successfully either way, just without GOOGLE_API_KEY ever reaching spring.ai.google.genai.api-key, so the failure surfaced two layers downstream as a Gemini authentication error instead of pointing at its real cause.

Moderate — found & fixed IGNORED emails were reclassified by Gemini on every single fetch

Deduplication originally only checked the tickets table — but IGNORED emails deliberately get no ticket row, and this app's readonly Gmail scope means it never marks a message read. Against a real inbox, not just a handful of hand-sent test emails, that meant every unrelated, still-unread message got reclassified by Gemini on every fetch, forever, indistinguishable in the UI from genuine new work. Fixed with a second table, processed_emails, recording every email_id the pipeline finished for — ticketed or not — checked before the pipeline runs at all rather than only at insert time. Verified against the shared database mid-session: 55 rows in processed_emails versus 7 in tickets, matching 7 real classifications plus 48 IGNORED or unrelated messages, all correctly remembered on the next fetch.

Moderate — found & fixed Chunking under Gmail's batch cap wasn't enough — its per-user concurrent-request limit still silently dropped messages

Even with every batch under Gmail's 100-inner-request cap (previous finding), the same 228-message run failed 125 of them individually with "Too many concurrent requests for user" — a separate, undocumented limit, because Gmail's backend fans a batch's inner requests out concurrently rather than processing them one at a time. No exception surfaced; fetchUnreadEmails() just silently returned fewer emails than existed. Fixed two ways at once: MAX_BATCH_SIZE dropped from 100 to 10 to keep in-flight requests under whatever the real concurrency ceiling is, and a retry-with-backoff pass re-fetches whatever still fails after each round, up to MAX_FETCH_RETRIES times. Re-run against the same live inbox afterward: 204 of 228 messages fetched cleanly; the remainder simply aren't marked processed, so they're retried on the next fetch rather than lost.

Info No streaming, one email at a time, and the injection surface from §3.3

Every node blocks synchronously on its own Gemini call rather than using ChatClient's streaming API (§2.6 covers where LangGraph4j's own stream() would need to plug in first). DashboardView runs its fetch batch on a single-threaded ExecutorService, so exactly one Gemini call is ever in flight regardless of how many unread emails a fetch pulls in. Neither is a bug so much as a scope boundary this pipeline hasn't needed to cross yet.

Info Zero permanent test coverage, for everything that touches Gemini or Gmail

Each fix above was confirmed with a real @SpringBootTest hitting the live Gemini API and the real shared database (or, for the Gmail-batching fixes, a standalone script against the real inbox), then deleted or discarded immediately afterward — deliberately, since a test that bills a real API key and needs a credential no CI environment has isn't fit to leave in the suite as-is. That still holds for anything touching Gemini or Gmail. It doesn't hold everywhere, though: a later pass added PropertyManagementStateSerializerTest as a real, permanent addition to the suite — pure JSON round-trip logic against in-memory records, no network or credential dependency, so nothing about it needed to be thrown away. It's also the one test guarding §2.7's fix directly: it fails the build if a future typed field is added to state without a matching TYPED_FIELDS entry, the exact silent-degradation risk that fix introduced.

Positive Provider-native structured output, verified against a real key, first try

The one piece of this port with no ambiguity in Spring AI's documentation about whether it would actually work: useProviderStructuredOutput() against Google GenAI returned a correctly-typed, correctly-populated UniversalRoutingData on the very first successful graph invocation (once the two threading and serialization bugs above were out of the way) — senderType=tenant, propertyAddress=425 Oak Street, unitNumber=4B, classification=MAINTENANCE, priorityLevel=HIGH, extracted from a real test email with no hand-tuning of the prompt or the schema needed.
